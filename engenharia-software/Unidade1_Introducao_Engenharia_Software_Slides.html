Ponto de Partida
Por que software falha?

Projetos de software falham menos por falta de programação isolada e mais por requisitos mal compreendidos, comunicação frágil, mudanças sem controle, estimativas irreais e ausência de processo. Engenharia de Software existe para reduzir essa incerteza.

Fundamentos e
Modelos de Processo
Engenharia de Software aplica princípios, métodos e ferramentas para produzir software de qualidade, dentro de limites reais de prazo, custo e escopo.
Software
Não é só código
I

Instruções executáveis

Programas, serviços, scripts, regras e integrações que realizam funções.

D

Estruturas de dados

Dados organizados para entrada, processamento, armazenamento e saída.

M

Modelos e documentação

Requisitos, diagramas, manuais, testes e decisões que permitem manutenção.

O produto de software continua mudando depois da entrega. Por isso qualidade inclui manutenibilidade, testabilidade, confiabilidade e capacidade de adaptação.

Princípios
Ideias que ajudam a domar complexidade
A

Abstração

Focar no essencial e ocultar detalhes que ainda não importam.

D

Dividir para conquistar

Quebrar problemas grandes em partes menores e compreensíveis.

O

Ocultação

Esconder decisões internas e expor interfaces claras entre módulos.

C

Completeza e consistência

Evitar lacunas, conflitos e interpretações incompatíveis.

Crise do Software
Quando construir software ficou difícil demais
P

Prazos e custos

Projetos estouravam cronogramas e orçamentos com frequência.

Q

Qualidade baixa

Erros, falhas, desempenho ruim e sistemas difíceis de usar ou manter.

R

Requisitos frágeis

Necessidades mal entendidas, mudanças tardias e comunicação insuficiente.

A resposta foi tratar software como engenharia: processo, documentação útil, métricas, validação, controle de mudanças e aprendizagem contínua.

Mitos
Crenças que bagunçam projetos
1

Adicionar mais pessoas em um projeto atrasado não garante aceleração; pode aumentar comunicação e retrabalho.

2

Software funcionando não significa software pronto; ainda há testes, documentação, implantação e manutenção.

3

Mudanças tardias costumam custar mais porque afetam arquitetura, testes, dados e expectativas.

4

Boa programação não substitui gestão, análise de requisitos, comunicação e validação com interessados.

Modelos de Processo
Escolha pelo contexto

Cascata

Modelo linear e sequencial. Funciona melhor quando requisitos são estáveis e bem conhecidos, mas é pouco flexível para mudanças tardias.

Atividade — 15 min
Qual modelo você escolheria?
Desafio

Escolha um projeto real ou hipotético e compare Cascata, Espiral e Incremental. Indique o modelo mais adequado e justifique com base em clareza dos requisitos, riscos, prazo, custo e necessidade de feedback.

1

Contexto

Descreva produto, usuários, restrições e incertezas.

2

Comparação

Mostre vantagens e limitações de cada modelo no projeto escolhido.

3

Decisão

Defina o modelo e explique o impacto esperado no desenvolvimento.

Sugestão de Resolução
Exemplo: sistema de reservas de clínica
C

Cascata

Útil se regras, integrações e relatórios já estiverem fechados. Risco: mudanças de agenda e convênios podem chegar tarde.

E

Espiral

Boa opção se há riscos altos, como integração com prontuário, LGPD e pagamento. Exige mais gestão.

I

Incremental

Escolha recomendada: entregar cadastro, agenda, reserva, confirmação e relatórios em incrementos com feedback rápido.

Justificativa: o produto tem valor em partes independentes e provavelmente receberá ajustes de fluxo. O incremental reduz espera, valida hipóteses e mantém espaço para mudanças.

Requisitos
Requisitos conectam necessidades dos interessados ao sistema que será projetado, construído, testado e mantido.
Tipos
Usuário, sistema, função e qualidade
U

Requisitos de usuário

Descrição em linguagem natural, mais próxima do negócio, dos serviços esperados e das restrições gerais.

S

Requisitos de sistema

Especificação detalhada de funções, serviços, limites operacionais e critérios técnicos.

Funcionais
O que o sistema deve fazer
A

Autenticar

Permitir login, logout, recuperação de senha e controle de sessão.

C

Cadastrar

Criar, consultar, atualizar e remover registros.

R

Relatar

Gerar relatórios, filtros, indicadores e exportações.

N

Notificar

Enviar e-mails, alertas ou mensagens quando eventos ocorrerem.

Requisitos funcionais descrevem serviços, entradas, saídas, exceções e regras de negócio. Ambiguidade aqui vira retrabalho no desenvolvimento.

Não Funcionais
Como o sistema deve se comportar
Perf

Desempenho

Tempo de resposta, throughput, volume de dados e usuários simultâneos.

Seg

Segurança

Privacidade, autenticação, autorização, auditoria e proteção contra uso indevido.

Uso

Usabilidade

Facilidade de aprender, eficiência, prevenção de erros e satisfação.

Transforme em mensurável

Em vez de “o sistema deve ser fácil de usar”, prefira: “após quatro horas de treinamento, usuários experientes devem executar as funções principais com média máxima de dois erros por hora”.

Sugestão de Resolução
Biblioteca: gabarito comentado
F

Funcionais

Buscar livros; cadastrar/remover/atualizar livros; notificar por e-mail quando reserva estiver disponível; registrar empréstimos/devoluções; gerar relatórios mensais.

NF

Não funcionais

Privacidade dos dados; busca em até 2 segundos; compatibilidade com Chrome/Firefox/Safari; 1000 usuários simultâneos; design intuitivo e amigável.

Boa discussão para a turma: alguns requisitos não funcionais podem gerar requisitos funcionais, como logs de auditoria para atender segurança e privacidade.

Controle de
Versões
Colaboração exige histórico, rastreabilidade, recuperação e regras claras para mudar sem perder controle.
GCS
Gerenciamento de Configuração de Software
ID

Identificar

Itens de configuração: código, docs, scripts, modelos, testes e releases.

CTRL

Controlar

Avaliar e aprovar mudanças, evitando alterações invisíveis.

QA

Garantir

Preservar integridade e coerência entre versões.

REP

Relatar

Saber quem mudou, quando, por quê e com qual impacto.

Funções
Versionar é lembrar com precisão
1

Acessar versões anteriores e recuperar o projeto quando algo quebra.

2

Auditar autor, data, conteúdo e motivo de cada mudança.

3

Evitar conflitos e permitir desenvolvimento paralelo.

4

Centralizar colaboração em um repositório com histórico compartilhado.

Baselines e Branches
Referências estáveis e caminhos de mudança
B

Baseline

Conjunto aprovado de itens que vira referência formal. Pode marcar requisitos, arquitetura, desenvolvimento ou produto entregue.

Br

Branch

Linha paralela de desenvolvimento usada para trabalhar isoladamente e depois integrar por merge.

Na prática: uma tag pode marcar a versão entregue; uma branch pode isolar uma nova funcionalidade sem quebrar a linha principal.

Git e GitHub
Ferramenta e plataforma não são a mesma coisa
Git

Controle de versão

Software livre, distribuído, rápido, com commits, branches, merges e histórico local.

Hub

Hospedagem e colaboração

Plataforma para repositórios remotos, pull requests, issues, revisões, páginas e automações.

Seu primeiro repositório
Desafio

Crie uma conta no GitHub, configure o Git, crie um repositório, clone localmente, adicione um pequeno projeto, faça o primeiro commit e envie para o repositório remoto.

git configNome e e-mail
git cloneCopiar remoto
git add .Preparar arquivos
git commitSalvar versão

Sugestão de Resolução
Roteiro comentado de Git
1

Configuração: definir nome/e-mail com git config --global user.name e git config --global user.email.

2

Primeiro envio: criar arquivos, executar git add ., git commit -m "Primeiro commit" e git push origin main.

3

Observação: algumas bases antigas usam master; confirme o nome da branch com git branch.

Sugestão de Resolução
Solução híbrida
AnáliseEntrevistas e requisitos essenciais.

ScrumSprints de duas semanas.
